When I pitch an AI solution to an executive, I start with where we are in the AI paradigm. The technical picture has to serve a business question: what work the proposed system would improve, what an acceptable result would be, and who remains responsible when it acts or gets something wrong. An explanation of the model is useful only insofar as it helps assess that proposal.

The distinction I want to make clear is between the model's output and the system that turns that output into actions. The model, the surrounding software and the humans approving consequential steps have different responsibilities. The pitch needs to make those responsibilities visible, rather than presenting the agent as one undifferentiated capability.

## What the model and its surrounding software do

A text-generating language model processes tokens and produces scores for what can come next. The system selects output from those scores. That gives it a way to generate text, not independent access to a business application. Tool calling lets the model request an action; the surrounding software decides whether and how that request is executed.

By harness, I mean that surrounding software: it manages the model's requests, tool execution and repeated steps. It can coordinate sub-agents, each working with its own context, and collect their results. Those results still have to be checked; delegation does not guarantee correctness.

Context engineering supplies the information relevant to the task within a limited context window. That may include business documents, tool results and instructions. Compaction can summarize earlier material to make room, but it can also omit details. The question for the proposal is which information must remain available and how the system will obtain it.

Instruction files and skills are ways to organize some of that context. AGENTS.md describes project and directory instructions for supporting coding agents; the documented convention gives more local instructions precedence when they conflict.[^agents-md] Agent Skills packages task instructions and optional resources in a folder, with detailed instructions loaded when needed.[^agent-skills] The precise loading and instruction rules depend on the harness. Neither kind of file is an access-control boundary.

## What stays deterministic in an agentic system

For every agentic system, you have to decide how much of it is grounded in your software-defined topology and how much needs the model's probabilistic output. By software-defined topology, I mean the shape of the system as it is written in code before the model runs: the sequence of steps, which tools are available at each step, and which actions are allowed at all. The model decides inside that shape, and where a step has to follow a fixed rule, the code enforces that rule.

Permissions and approval requirements belong in that software, not just in instructions asking the model to behave. If an action requires human approval, the tool or service carrying it out should check that approval before executing it. Deterministic code can still have defects; it needs testing and monitoring too.

## Evidence, traces, audit logs and human approvals

Evidence is the first part. Agents can say that they did something without doing the work, so I ask for the evidence produced while the request was being processed: the resulting artifact, the tool response or a check of the changed system state, as appropriate to the task.

An agent's explanation of why it chose a path can help someone review the result, but that explanation is generated text. It is not proof that the action happened, or a reliable record of the internal process that produced the choice. Evidence should be checked against the tools and systems involved.

Traces are the second part, as in application performance management. They connect the steps in a request so that a reviewer can follow model calls, tool requests and responses, and failures across the workflow. A trace shows what was recorded; it does not establish that every recorded action was correct.

Audit logs serve a related purpose: recording who or what requested an action, the permission or human approval used, and what the executing system reports happened. They should be produced by the software carrying out the actions, with suitable access and integrity controls, rather than relying only on an agent's final summary.

Together, these records make a system more assessable. They do not, on their own, establish enterprise readiness; the proposal still needs criteria for acceptable output, testing, operational ownership and a way to handle failure.

## A case from Anthropic's cybersecurity evaluations

In July 2026, Anthropic disclosed three incidents in which models running in a partner's capture-the-flag evaluations reached real systems. According to its report, the prompts described an isolated simulation, but a misconfiguration left internet access available.[^mythos]

In one incident, Claude Mythos 5 published a malicious package to the real PyPI registry while treating it as part of the simulation. Anthropic reported that the package was available for roughly an hour and ran on 15 real systems. One was a cybersecurity company's scanner; the package exfiltrated that company's credentials, which the model then used to access further infrastructure.

Anthropic said that multiple factors contributed and described the incidents as closer to harness and operational failures than model alignment failures. It identified validation of internet access paths and real-time monitoring among the measures that could have prevented the incidents or surfaced the problem sooner.

The lesson I take for an enterprise proposal is that a description of the environment is not a control over the environment. Telling a model that it has no internet access is different from enforcing that boundary. The same distinction applies when a proposal says that an agent can only act within an approved scope.

## What this means for the pitch

The technical explanation should let an executive ask concrete questions about the proposed workflow. What is the current task, and what improvement would justify changing it? Which inputs and actions are in scope? Who checks the output, and which actions require approval? What happens when the model fails, and what records let someone investigate?

The proposal should distinguish expected benefits from measured results. A working demonstration can show that a path is possible; a trial needs to establish how often the system produces acceptable work, how much checking it requires and whether the improvement justifies the cost and risk. The necessary technical depth depends on those decisions, not on covering every detail of model generation.

## What I am testing now

I am working on a trial project for an internal use case, where I focus on designing the harness and context around a model and on understanding which models and sub-agents respond better to a task.

I do not have results to report here. The trial is the setting for examining those choices, not evidence yet that the system meets a production standard. That distinction is part of the pitch too: what the system has demonstrated, what remains uncertain, and what the next test needs to establish.
