When I pitch an AI solution to an executive, I start with where we are in the AI paradigm. A language model takes text, turns it into numbers, processes them through a lot of math, mostly matrix multiplication, and gives text back. On its own it cannot interact with the world; tool calling is how it does. Around the model sits the harness, the deterministic software that runs it in loops, hands work to sub-agents and manages its context, and context engineering, which gives a model trained on general knowledge the specifics of your situation inside a limited context window.

Once you build an agentic system, you also have to decide how much of it is deterministic and how much needs the model's probabilistic output, where only humans can approve, and how you prove what the agents did: evidence, traceability and audit logs. Without that visibility, enterprise-grade reliability and accountability are very hard to achieve.

In this essay, I go through each of these in turn; then I describe a case from Anthropic's cybersecurity evaluations, what all of this means for the pitch, and the trial project I am working on now.

## Where we are in the AI paradigm

I start here so that the executive has a working picture of the machine before the pitch.

The one-line version is this: text goes in, it becomes numbers, the model does math on those numbers, and probable text comes out.

## What the model does

The tokenizer splits the text into tokens, and each token becomes a vector of numbers, taken from a lookup table that the model learned in training. Inside the transformer, attention works out how each token relates to the others, and at the end, softmax turns the model's scores into probabilities and sampling picks one token, shaped by settings such as temperature, top-k and top-p. Then the model repeats this, one token at a time, until the answer is done.

## Tool calling

The model itself cannot interact with the world; that is where tool calling comes in. Tool calling lets it ask for actions.

## The harness

A harness runs the model in loops, lets it use sub-agents and helps it with context engineering.

Harness engineering is about controlling the model with deterministic software: where the model gives probabilistic output, some decisions are made deterministically.

## Context engineering

A model is trained on a large, general body of text from many fields, so it has good knowledge of the world; but it does not know your specific situation, your business use case or the problem you are solving. Context engineering is how you give it those specifics.

The context window, the amount of text a model can take into account at one time, is limited: some models get around 300,000 tokens, and some get up to a million.

Sub-agents are one technique. When a task is big, the model structures it and hands parts of it to sub-agents, each with its own limited context; each sub-agent works and returns its results, so the main model manages its context without losing it.

Compaction is another technique: it condenses what is already in the context so that there is room for the work that follows. It runs at set intervals or automatically.

A third is skills files, AGENTS.md and other Markdown files, placed in different layers, which the model and its harness perceive in different ways.

The layers are the user, the project and the directory. Instructions at the user level sit in the harness's own configuration and apply to everything you work on; at the project level they sit in an AGENTS.md file at the root of a repository; at the directory level they sit in an AGENTS.md file inside part of it. The harness reads the nearest AGENTS.md to the file being worked on, and when instructions conflict, the closest one wins; what you say in the chat overrides all of them.[^agents-md] A skill is treated differently again: it is a folder with a SKILL.md file, and the harness reads the names and descriptions of the skills available to it, then loads the full instructions of one only when a task matches it.[^agent-skills] The model perceives all of this as text in its context; it is the harness that decides what enters that context, and when.

## What stays deterministic in an agentic system

For every agentic system, you have to decide how much of it is grounded in your software-defined topology and how much needs the model's probabilistic output. By software-defined topology, I mean the shape of the system as it is written in code before the model runs: the sequence of steps, which tools are available at each step, and which actions are allowed at all. The model decides inside that shape, and where a step has to be predictable, the code decides instead.

## Evidence, traces, audit logs and human approvals

Evidence is the first part. Agents can say that they did something without doing the work, so I ask for the evidence produced while the request was being processed.

I also ask the agents to explain, alongside the output, why they picked a decision, a path of reasoning or a line of research.

Traces are the second part, as in application performance management. Tools such as Instana (acquired by IBM)[^instana] trace a user request end to end, through microservices, a monolith or cloud services, and show what each hop produced. An agentic system needs the same, so that when something goes wrong, you can track what happened and where to fix it.

Audit logs are the third part, kept for the agents' actions and for the evidence they produce.

Human approvals are the last part. Humans grant permission for agents to do specific things, and guardrails make sure that only humans can approve certain decisions or do certain things.

The traceability and the audit logs are how you track all of this: the evidence, the agents' actions and the human approvals.

Without this, enterprise-grade stability, reliability, accountability and responsibility are very hard to achieve. All of it takes harness engineering through deterministic software, and context engineering, where you are careful about what goes into the agentic AI models' context.

## A case from Anthropic's cybersecurity evaluations

In July 2026, Anthropic disclosed that Claude Mythos 5, in a capture-the-flag evaluation run by a partner, Irregular, reached the real internet through a misconfiguration. It had been told that it was in a simulation with no internet access.[^mythos]

The model concluded that it was still in a simulation, because it did not recognize the certificate authorities on its connections and the 2026 system date looked staged to it. It never revisited that conclusion.

It needed an email address to create a PyPI account, and a phone number to create an email address; it tried and failed to get funds for a phone number, and then found a free email provider.

It published a package with hidden code, which was live for about an hour and ran on 15 real systems, including a cybersecurity company's scanner, and the code exfiltrated that company's credentials.

In its post, Anthropic called the incidents it disclosed closer to a harness and operational failure than to a model alignment failure, and said that careful validation of all internet access paths before the evaluation, and real-time monitoring of the evaluation logs, would have helped to surface the problem sooner.

This is the case for deciding what stays deterministic, and for the evidence, traces and audit logs an agentic system needs.

## What this means for the pitch

Once the executive has this picture, I frame the solution in the same terms, layer by layer: which model does the work, the harness that runs it, the context the system is given, what stays deterministic and what humans approve, and the evidence, traces and audit logs that come out of it. The picture came first, so every part of the pitch can be checked against it: what the layer does in our case, and where the humans sit. I end on the evidence, the traces and the audit logs, because that is the part that decides whether the system can carry enterprise work.

## What I am testing now

I am working on a trial project for an internal use case, where I focus on designing the harness and context around a model and on understanding which models and sub-agents respond better to a task.

The trial is still running, so I do not have results to report yet. What I can say so far is what it measures: the same task, run through different models and sub-agents, with the results compared against each other.

## Close

What I explain before I pitch is the machine itself, in the order its parts connect: a model that gives probabilistic output; tool calling, which lets it ask for actions; a harness and a context built around it; the part that stays deterministic; the humans who approve what matters; and the evidence, traces and audit logs that show what the agents did. The pitch comes after that picture, described in the same terms, so that an executive can judge the solution part by part. My trial project is the same construction at a small scale, and it is where I bring the pitch from.

[^agents-md]: AGENTS.md is an open format for guiding coding agents, stewarded by the Agentic AI Foundation under the Linux Foundation. See [AGENTS.md](https://agents.md).
[^agent-skills]: Agent Skills is an open format for giving AI agents new capabilities, originally developed by Anthropic and released as an open standard. A skill is a folder with a SKILL.md file carrying a name, a description and instructions; an agent reads the name and description of each skill at startup and loads the full instructions only when a task matches one. See the [Agent Skills overview](https://agentskills.io).
