When I pitch an AI solution to an executive, I start with where we are in the AI paradigm. A language model takes text, turns it into numbers, processes them through a lot of math, mostly matrix multiplication, and gives text back. Tool calling lets it ask for actions, and the software around it decides whether and how those actions run.

Once you build an agentic system, you also have to decide how much of it is deterministic and how much needs the model's probabilistic output, where only humans can approve, and how you prove what the agents did. I want the executive to understand those parts so that we can talk about the work the solution would improve, what a useful result would be, and who is responsible for it.

## What the model and its surrounding software do

By harness, I mean the software around the model that runs it in loops, lets it use tools and helps manage its context. It can hand parts of a task to sub-agents, each with its own context, and bring their results back. Those results still need to be checked before the system uses them.

By context engineering, I mean giving the model the specifics of the situation, the business use case and the problem we are solving, inside a limited context window. Some of that comes from documents and instructions, and some comes back from tools. Compaction condenses earlier context so that there is room for what follows; because details can be lost, we need to decide what information the system must keep available.

Skills files, AGENTS.md and other Markdown files are ways to organize the instructions. In coding agents that follow the AGENTS.md convention, instructions can sit at the project level or inside a directory, with the closer file taking precedence when they conflict.[^agents-md] A skill carries instructions for a task in a folder, and an agent that supports it can load the full instructions when needed.[^agent-skills] The harness decides what it reads and when. These files give instructions to the model; permissions still have to be enforced in the software.

## What stays deterministic in an agentic system

For every agentic system, you have to decide how much of it is grounded in your software-defined topology and how much needs the model's probabilistic output. By software-defined topology, I mean the shape of the system as it is written in code before the model runs: the sequence of steps, which tools are available at each step, and which actions are allowed at all. The model decides inside that shape, and where a step has to follow a fixed rule, the code enforces that rule.

For example, if only a human can approve an action, the software carrying out that action needs to check for the approval before it runs. Telling the model to ask is not enough. The code enforcing the rule also needs to be tested and monitored.

## Evidence, traces, audit logs and human approvals

Evidence is the first part. Agents can say that they did something without doing the work, so I ask for the evidence produced while the request was being processed. Depending on the task, that can be the file produced, the tool's response or a check of what changed in the system.

I also ask the agents to explain why they picked a decision, a path of reasoning or a line of research. That can help me review the output, but the explanation is generated text too; I still need evidence from the tools and systems to know what happened. The explanation does not give me direct access to the model's internal process.

Traces are the second part, as in application performance management. I want to trace a request end to end, through the model calls, the tools and the responses, so that when something goes wrong, I can track what happened and where to fix it. I still have to look at those records to judge whether the actions and the result were right.

Audit logs are the third part, kept for the agents' actions and the evidence they produce. The software carrying out an action should record who or what requested it, the approval used and what happened, with controls over who can access or change that record.

Human approvals are the last part. Humans grant permission for agents to do specific things, and the software enforces which decisions or actions require that approval. The traces and audit logs need to connect those approvals to the actions that followed.

Without this visibility, enterprise-grade reliability and accountability are very hard to achieve. We also need to test the quality of the output and decide who handles a failure when the system is in use.

## A case from Anthropic's cybersecurity evaluations

In July 2026, Anthropic disclosed three incidents in which models running in a partner's capture-the-flag evaluations reached real systems. According to its report, the prompts described an isolated simulation, but a misconfiguration left internet access available.[^mythos]

In one incident, Claude Mythos 5 published a malicious package to the real PyPI registry while treating it as part of the simulation. Anthropic reported that the package was available for roughly an hour and ran on 15 real systems. One was a cybersecurity company's scanner; the package exfiltrated that company's credentials, which the model then used to access further infrastructure.

Anthropic said that multiple factors contributed and described the incidents as closer to harness and operational failures than model alignment failures. It identified validation of internet access paths and real-time monitoring among the measures that could have prevented the incidents or surfaced the problem sooner.

This is why I want the boundaries enforced in the software. If the system is meant to have no internet access, that needs to be true of the environment, not just something the model has been told. The evidence, traces and audit logs then help us check what the agents did within that environment.

## What this means for the pitch

Once the executive has this picture, I want to explain the solution in the same terms: what work it would improve, which model does the work, what context it gets, what stays deterministic, and where the humans sit. The evidence, traces and audit logs should let us check the claims we make about what the system did.

A demonstration can show that the system can do a task. Before saying it is ready for enterprise work, I would want to know how often the result is usable, how much checking it needs, and whether the time and effort saved justify the cost and risk. Those are the reasons for explaining the parts of the system before asking someone to rely on it.

## What I am testing now

I am working on a trial project for an internal use case, where I focus on designing the harness and context around a model and on understanding which models and sub-agents respond better to a task.

The trial is still running, so I do not have results to report yet. It is where I am working through these choices on a small scale, before making claims about what the system can reliably do.
