My work with colleagues at a US health system is about exploring things first, and helping them explore where AI becomes the best tool and gives productivity and efficiency gains.

The department newsletters are one example. They also show how a workflow I develop can become a skill that colleagues can use, and why the surrounding tools matter as much as the model.

Exploring first means looking at the task: which steps repeat, what the output has to be, and whether AI makes that work easier. Time and effort matter, but so do output quality and the work needed to check and correct it. I do not report measured time savings here; this is an account of the workflow and the tool choices behind it.

## The department newsletters

There has been a need for internal newsletters, monthly and half-yearly, one for each department, each one created at the department level.

I build them with GitHub Copilot CLI, and they come out engaging and professional, close to what a designer would produce.

Without AI, we would not have thought of the task this way, and we would not have done it.

## Choosing a tool for the newsletter workflow

For this workflow, I use GitHub Copilot CLI rather than Microsoft 365 Copilot because I want to keep iterating on the same files and folders under Git version control. That is a choice about the workflow I use, not a claim that Microsoft 365 Copilot cannot help create a newsletter.

By harness, I mean the software around the model that manages its requests, tool use and repeated steps. GitHub Copilot in VS Code and GitHub Copilot CLI provide ways to work on a local set of files, which fits this task.

By context, I mean the specifics of my situation that the model is given. Context engineering is giving the model those specifics inside a limited context window.

The harness coordinates the model's work on the newsletter files. The environment is the folder under Git version control, where I can inspect changes and return to a saved version. The context is the department material supplied for the task. These are separate parts of the workflow: version control records changes, but it does not establish that the newsletter's contents are correct.

## Turning a task into a skill colleagues can run

When a task works in GitHub Copilot CLI, I transcribe it into a durable skill in the Agent Skills format,[^agent-skills] so that I can distribute it to colleagues. A skill is a folder with a SKILL.md file containing its name, description and instructions; it can also contain scripts, templates and reference files. A supporting agent can load the metadata first and the full instructions when the skill is needed, rather than keeping every skill's instructions in context.

We have used these skills for PowerPoint presentations, HR headcount analysis and governance, risk and compliance (GRC) work.

The folder makes the instructions portable, but it does not make the whole environment portable. The receiving agent has to support the format, and any required software, permissions and data access still have to be available. The skill can describe those requirements; it does not grant access or guarantee the same result on another machine. Its output still needs review.

[^agent-skills]: The [Agent Skills specification](https://agentskills.io/specification) defines the SKILL.md file, optional scripts and resources, progressive loading, and a compatibility field for environment requirements. Support for execution and permissions depends on the agent implementation.

## Setting colleagues up

I have set up more than twenty colleagues with VS Code, GitHub Copilot, Python and Node.js.

Installing those tools is only part of making a workflow usable. The environment also has to provide the access and dependencies the particular task needs. For workplace use, the choice of data, accounts and tools has to follow the organization's requirements; a working local setup is not, by itself, authorization to process internal information.

## Advising on which tool for which job

I champion GitHub Copilot CLI internally, and I advise on when to use Microsoft 365 Copilot and when to use GitHub Copilot CLI.

My rule of thumb is to consider Microsoft 365 Copilot for work with organizational content and GitHub Copilot for builds where I iterate on the same files many times. The actual choice depends on the task, the available integrations and the access allowed for it, rather than a permanent boundary between the products.

The newsletter workflow is useful to me because it connects a real task to a tool, a set of files and instructions that can be shared. The next question is whether a colleague can use that workflow successfully in their own permitted environment, with output they can check. A skill folder helps with that handover; it is not the whole handover.
